## 1. ROS 2 기초

### Q. 워크스페이스가 뭐길래 venv와 무관하다는 거지? colcon은 뭐고?

**ROS 2 워크스페이스는 "ROS 버전의 venv"다.** venv를 쓰는 이유는 파이썬 라이브러리를 시스템에 어지럽히지 않고 프로젝트 폴더 안에 격리 설치하고, `source venv/bin/activate`로 켜서 쓰기 위해서다. 워크스페이스가 정확히 같은 개념이다:

| | Python venv | ROS 2 워크스페이스 |
|---|---|---|
| 정체 | 라이브러리를 담는 격리 폴더 | ROS 패키지를 담는 격리 폴더 (= 이 프로젝트 폴더) |
| 설치 명령 | `pip install` | `colcon build` |
| 설치 결과가 가는 곳 | `venv/lib/...` | `install/` 폴더 |
| 활성화 | `source venv/bin/activate` | `source install/setup.bash` |

"venv와 무관하다"는 말은 워크스페이스가 venv와 경쟁하거나 겹치는 게 아니라 **애초에 별개의 격리 시스템**이라는 뜻이다.

`colcon`은 ROS 2의 설치 도구로, venv 세계의 `pip`에 해당한다. `colcon build`라고 부르지만 파이썬 패키지의 경우 컴파일이 아니라 **`src/`의 코드를 `install/` 폴더로 복사하고 ROS가 찾을 수 있게 등록**하는 작업이다.

### Q. 보일러플레이트가 정확히 뭐야? 무슨 "형식"을 갖춘다는 거지?

보일러플레이트는 설치하는 라이브러리가 아니라, **형식을 갖추기 위해 매번 거의 똑같이 작성해야 하는 뼈대 파일들**이다. 이력서 양식 같은 것 — 이름 칸, 경력 칸은 누구나 똑같이 채우지만, 그 양식이 없으면 서류 접수 자체가 안 된다.

pip은 `pip install numpy` 하면 알아서 설치하는데, 이는 numpy 제작자가 "무슨 파일을 어디에 설치할지" 적은 명세서를 미리 만들어뒀기 때문이다. colcon도 똑같이 명세서가 필요하고, 그게 ROS 패키지의 보일러플레이트 3종이다:

| 파일 | 역할 |
|---|---|
| `package.xml` | "이 폴더는 ROS 2 패키지다"라는 신고서. 이름과 의존성(rclpy, dsr_msgs2 등)을 기록 |
| `setup.py` | `colcon build` 시 어떤 파이썬 모듈을 `install/`로 복사할지 정의하는 설치 목록 |
| `setup.cfg` | `ros2 run 패키지명 노드명` 한 줄로 실행할 수 있게, 실행 명령어 파일을 만들 위치 지정 |

colcon은 이 파일들이 없는 폴더는 패키지로 인식조차 하지 않는다. 노드 코드가 "내용물"이라면 보일러플레이트는 그걸 ROS 2가 인식할 수 있게 감싸는 "포장지"다.

### Q. package.xml에 적힌 rclpy, dsr_msgs2가 뭐야?

둘 다 노드 코드가 import하는 **라이브러리 이름**이다:

```python
import rclpy                                    # ROS 기능을 파이썬에서 쓰게 해주는 공식 라이브러리
from dsr_msgs2.srv import MoveLine, MoveJoint   # 두산이 배포한 "메시지 서식" 모음
```

- **rclpy** = ROS Client Library for Python. 노드 만들기, 토픽 발행, 서비스 호출 같은 ROS 기능의 파이썬 API. ROS 2를 설치하면 딸려 온다.
- **dsr_msgs2** = 두산 로보틱스가 만든 패키지. `MoveLine` 서비스의 "요청엔 좌표 6개, 응답엔 success" 같은 서식 정의만 모아둔 것.

`package.xml`에 이 둘을 적는 이유는 pip의 requirements.txt처럼 "이 패키지를 쓰려면 이것들이 먼저 있어야 한다"고 알려주기 위해서다.

### Q. ROS 2 인터페이스가 뭐야?

노드들끼리 대화할 때 쓰는 **"메시지 형식의 계약서"**다. 통신 방식은 세 종류:

- **토픽 (Topic)** — 방송. 한 노드가 계속 뿌리고, 원하는 노드가 구독. 응답 없음.
  예: fusion 노드가 `/strawberry/detection/pick_pose`로 딸기 위치를 계속 발행 → scan_executor가 구독
- **서비스 (Service)** — 전화. 요청하면 응답이 올 때까지 기다림. 1회성.
  예: planner가 `/dsr01/motion/move_line` 호출 → 로봇이 직선 이동 후 `success: true` 응답
- **액션 (Action)** — 배달 주문. 오래 걸리는 작업을 시키고, 중간 진행상황(feedback)을 받다가 최종 결과를 수신. 취소 가능.
  예: `SafeGrasp` — 그리퍼가 닫히는 동안 전류값 피드백을 받다가 파지 성공/실패를 최종 수신

인터페이스 "타입"(예: `dsr_msgs2/srv/MoveLine`)은 이 계약서의 서식이다. 이 프로젝트에서 쓰는 서식 목록은 [`pipeline_overview.md`](pipeline_overview.md) 참고.

### Q. "소스 트리"와 "패키지 share"가 무슨 말이야? 데이터 전용 미니 패키지는 뭐고?

- **소스 트리** = `src/` 아래의 원본 파일들.
- **share** = `colcon build`가 `install/패키지명/share/`에 만드는 **설치본**. venv로 치면 "내 프로젝트 폴더의 코드" vs "pip install로 venv에 복사된 코드"의 관계다. 노드가 `get_package_share_directory("패키지명")`으로 찾는 곳이 share다.

같은 설정 파일이라도 노드마다 찾는 위치가 다를 수 있다. 이 프로젝트에서 `planner_bootstrap.py`는 소스 트리를 1순위로, `sim_executor_bridge_node`는 share만 찾아서 cuRobo 설정을 이중 배치했다.

**데이터 전용 미니 패키지**는 코드 없이 설정 파일만 담은 ROS 패키지다. 노드가 특정 패키지 이름(`e0509_gripper_description`)으로 설정을 찾도록 코딩되어 있으면, 그 이름의 패키지가 워크스페이스에 존재해야 share 조회가 성공한다. 그래서 설정 파일 + 보일러플레이트만으로 이루어진 패키지를 만든 것. 각 YAML 파일의 역할은 [`config_reference.md`](config_reference.md) 참고.

## 2. 리눅스 / 우분투

### Q. "우분투 기본 저장소에 CUDA 툴킷이 없다"는 게 무슨 말이야? apt가 기본 저장소야? 키링은 뭘 하는 작업이지?

앱스토어 비유가 딱 맞는다:

- **apt(= apt-get)** = 스마트폰의 "앱스토어 앱". 패키지 관리자일 뿐, 그 안에 앱이 들어있지 않다.
- **저장소(repository)** = 스토어 서버. 어떤 저장소를 쓸지는 PC에 등록되어 있다 (`/etc/apt/sources.list*`). `sudo apt update`가 하는 일이 "등록된 모든 저장소에서 최신 패키지 목록 받아오기"이고, `apt install X`는 그 목록에서 X를 찾는다. "패키지를 찾을 수 없습니다"는 등록된 저장소 어디에도 그 이름이 없다는 뜻.
- **기본 저장소** = Ubuntu 설치 시 자동 등록되는 Canonical 공식 저장소. 직접 검수·관리하는 소프트웨어만 담아 **버전이 보수적**이다. Ubuntu 22.04 기본 저장소의 CUDA는 출시 시점(2022년)에 얼려진 11.5뿐이라, 12.x가 필요하면 NVIDIA가 직접 운영하는 저장소를 **추가 등록**해야 한다. 갤럭시 폰에 삼성 스토어를 추가하는 것과 같다.
- **키링(keyring)** = 위조 방지 도장. 저장소 추가는 "이 서버의 프로그램을 root 권한으로 설치하겠다"는 뜻이라 보안상 민감하다. 저장소 운영자는 패키지 목록에 암호학적 서명을 하고, 사용자는 운영자의 공개키를 미리 받아둔다(`/usr/share/keyrings/`). apt는 다운로드마다 "이 서명이 정말 NVIDIA 키로 만든 게 맞나"를 검증하고 안 맞으면 거부한다. `cuda-keyring` 패키지 설치 = NVIDIA 공개키 등록 + NVIDIA 저장소 주소 추가.

정리: **apt는 스토어 앱, 저장소는 스토어 서버, 기본 저장소는 우분투 공식 스토어(안정적이지만 낡음), 키링은 정품 인증 도장.**

## 3. 파이썬 환경과 의존성

### Q. 왜 모든 걸 하나의 venv에 넣을 수 없지?

**파이썬으로 컴파일된 라이브러리는 파이썬 마이너 버전에 묶인다.** ROS 2 Humble의 rclpy 등은 py3.10용으로 빌드되어 py3.11에서 import 자체가 안 되고, Isaac Sim 5.1.0은 py3.11을 요구한다. 그래서 이 프로젝트는 두 파이썬 세계가 ROS 토픽으로만 통신하는 구조다. 상세: README의 **"실행 환경 구조 — 두 개의 파이썬 세계"** 섹션.

### Q. "번들되어 있다"는 게 무슨 말이야?

**제품 상자에 전용 케이블이 동봉된 것**과 같다. 배포자가 "사용자 PC에 어떤 버전이 설치되어 있을지 모르니, 우리가 미리 빌드한 사본을 설치 파일 안에 같이 넣어 배포"하는 방식. Isaac Sim의 경우 NVIDIA가 py3.11용으로 빌드한 rclpy 사본이 확장 폴더 안에 통째로 들어 있다:

```
~/.venv/lib/python3.11/site-packages/isaacsim/exts/isaacsim.ros2.bridge/
├── humble/rclpy/   ← py3.11용으로 빌드된 rclpy + ROS 라이브러리(.so)
└── jazzy/rclpy/
```

사용자가 설치한 적 없고, 시스템 ROS와도 완전히 별개인 사본이다.

### Q. "sys.path에 등록된다"는 게 무슨 말이야?

`sys.path`는 **파이썬이 `import` 할 때 뒤지는 폴더 목록**이다. `import rclpy`를 만나면 파이썬은 이 목록의 폴더들을 순서대로 열어보며 rclpy를 찾고, 어디에도 없으면 `ModuleNotFoundError`를 낸다. venv를 activate하면 그 venv의 site-packages가 검색 경로에 들어오는 것과 같은 원리다.

파일이 디스크에 존재해도 `sys.path`에 없는 구석 폴더면 import가 안 된다. 그래서 번들 rclpy는 누군가 `sys.path.append(...)`를 실행해 줘야 import가 가능해지고, Isaac Sim에서는 ROS2 Bridge 확장의 시동 코드가 그 일을 한다 (아래 §4 참고).

### Q. setuptools 79.0.1, warp-lang 1.9.1 같은 "버전 고정"은 왜 하는 거야?

라이브러리 A가 라이브러리 B의 **특정 시점 API**에 의존해 작성됐는데 B가 그 후 방식을 바꾸면, B의 최신판을 깔았을 때 A가 깨진다. 이 프로젝트에서 실제로 두 번 발생했다:

| 고정 | 이유 |
|---|---|
| `setuptools==79.0.1` | colcon은 80 미만을 요구하고, cuRobo 빌드의 setuptools_scm은 최신 기능을 요구 → 둘을 동시에 만족하는 버전 |
| `warp-lang==1.9.1` | cuRobo 0.7.8은 `wp.torch` 서브모듈에 암묵적으로 접근하는데, warp 1.10부터 지연 로딩 방식이 바뀌어 `AttributeError`로 깨짐 |

"최신 버전이 항상 좋다"가 아니라, **의존하는 쪽이 검증한 버전 조합을 유지하는 것**이 안정성의 기본이다. pip가 자동으로 최신판을 딸려 오게 하는 경우(cuRobo 설치 시 warp 최신판)가 있어서, 설치 **순서**(A 설치 후 B 다운그레이드)까지 문서화해야 한다.

## 4. Isaac Sim

### Q. 확장(Extension)이 뭐고, 왜 켜져야 하지?

Isaac Sim은 하나의 거대한 프로그램이 아니라 **Kit이라는 얇은 뼈대 + 수백 개의 확장(플러그인)** 구조다. 물리 엔진, 센서, URDF 임포터, ROS 2 연동이 전부 개별 확장이고, 필요 없는 기능은 로드하지 않아 시작 속도와 메모리를 아낀다. 확장의 **시동 코드(on_startup)는 확장이 활성화될 때만 실행**되므로, 어떤 기능이 "설치되어 있는데도 동작하지 않는다"면 담당 확장이 꺼져 있을 가능성부터 확인한다.

### Q. Script Editor에서 `import rclpy`가 ModuleNotFoundError로 실패한 이유는?

세 가지 사실의 조합이다:

1. Isaac Sim은 py3.11이라 **시스템 rclpy(py3.10용)를 쓸 수 없다** (§3 참고)
2. 대신 py3.11용 rclpy가 `isaacsim.ros2.bridge` 확장에 **번들**되어 있다
3. 이 번들 rclpy는 확장의 시동 코드가 **sys.path에 등록해 줘야** import가 가능한데, 확장이 꺼져 있으면 그 코드가 실행되지 않는다

확장의 시동 코드는 sys.path 등록 외에도 ROS_DISTRO 결정, 번들 C 라이브러리(rcl, FastDDS) 로드, 브릿지 C++ 플러그인 로드, `import rclpy` 자가 테스트(성공 시 콘솔에 `rclpy loaded`)까지 수행한다. rclpy는 얇은 파이썬 껍데기이고 실제 일은 그 밑의 C 라이브러리들이 하기 때문에, sys.path만 수동으로 추가하는 우회는 통하지 않는다.

**해결**: Window → Extensions → "ROS2 Bridge" 검색 → ENABLED + AUTOLOAD. 내장 humble도 시스템 Humble과 같은 배포판·같은 기본 RMW(FastDDS)라 토픽 상호운용에 문제가 없다.

### Q. 확장 토글을 켜도 곧바로 꺼진 상태로 되돌아오는 건 왜야?

**확장이 켜지자마자 자가진단에 실패해 스스로를 다시 비활성화한 것**이다. ROS2 Bridge 확장의 시동 코드는 ROS 라이브러리(C `.so` 파일들) 로드를 시도하고, 실패하면 콘솔에 설정 안내를 출력한 뒤 `set_extension_enabled(..., False)`를 호출한다 — 사용자 눈에는 토글이 튕기는 것으로 보인다.

원인은 대부분 **실행 전 환경변수 누락**이다. `.so` 라이브러리 검색 경로(`LD_LIBRARY_PATH`)는 프로세스 시작 후에 바꿀 수 없어서, 내장 ROS 라이브러리를 쓰려면 Isaac Sim을 **실행하기 전에** `ROS_DISTRO`, `RMW_IMPLEMENTATION`, `LD_LIBRARY_PATH`(→ 확장의 `humble/lib` 폴더)를 지정해야 한다. 정확한 실행 명령은 README "Isaac Sim 실행" 섹션 참고.

일반화하면: **GUI에서 스위치가 저절로 되돌아오는 증상은 "안 눌린 것"이 아니라 "켜졌다가 초기화에 실패해 물러난 것"**일 가능성이 높으니, 콘솔/로그에서 실패 사유를 찾는 게 순서다.

### Q. 시뮬 로봇이 출렁이고 덜덜거리는 건 왜야? (joint drive stiffness/damping)

Isaac Sim(PhysX)에서 관절에 위치 명령을 주면 모터가 순간이동시켜 주는 게 아니라, 각 관절의 **drive**가 스프링-댐퍼처럼 토크를 만들어 목표를 쫓아간다:

```
토크 = stiffness × (목표각 − 현재각) + damping × (0 − 현재각속도)
```

- **stiffness(강성)**: 목표에서 벗어난 만큼 되돌리는 스프링의 세기. 낮으면 팔이 무거운 링크의 관성을 못 이겨 목표 주변에서 축 처지거나 출렁인다.
- **damping(감쇠)**: 움직임 자체에 저항하는 브레이크. 낮으면 목표를 지나쳤다가 되돌아오기를 반복하는 진동(덜덜거림)이 안 죽는다.

이 프로젝트에서 실제로 겪은 사례(2026-07-10): URDF 임포터가 넣어준 기본값이 stiffness 54~2648에 damping은 거의 0이었다 — 감쇠 없는 약한 스프링에 수 kg짜리 링크를 매단 셈이라, 이동 중 덜덜거리고 정지할 때 출렁였다. `robot_assembly.usd` 오버라이드로 팔 관절을 stiffness=1e5 / damping=1e4(강성의 10%)로 올려 해결했다. 위치 제어 로봇 팔은 "아주 강한 스프링 + 강성의 5~10% 감쇠"가 Isaac Sim의 통상 세팅이다.

주의할 점 두 가지. ① 실기는 제어기가 이 역할을 하므로 시뮬 게인은 **물리 정확도가 아니라 "명령 추종 품질"의 파라미터**다 — 시뮬에서 딱딱하게 움직이게 만드는 게 목적이면 크게 줘도 된다(PhysX는 implicit 적분이라 큰 강성에도 안정적). ② 게인은 USD의 joint drive 속성에 저장되므로, 코드가 아니라 **애셋(robot_assembly.usd)의 오버라이드**로 고치는 것이 맞다 — 원본 임포트 결과물은 건드리지 않는다는 이 프로젝트 원칙 그대로 (`docs/usd_structure.md` §3).

### Q. 로봇이 45mm만 가라고 했는데 팔 전체가 뒤집히며 바닥을 뚫은 건 왜야? (IK 다중해)

6축 팔에서 **같은 그리퍼 위치·자세(EE pose)를 만드는 관절 조합은 하나가 아니다.** 팔꿈치를 위로 접거나(elbow-up) 아래로 접거나(elbow-down), 어깨를 반대로 돌려 뒤로 팔을 뻗거나, 손목을 ±180° 뒤집어도 그리퍼는 같은 곳에 도달한다. 해석적으로 6축 팔은 최대 8개의 해 브랜치를 갖는다.

cuRobo 같은 **수치 IK는 무작위 seed 여러 개에서 최적화를 돌려 "포즈 오차가 가장 작은" 해를 내놓는데, 어느 브랜치의 해인지는 보장하지 않는다.** 브랜치가 달라도 포즈 오차는 똑같이 0이기 때문이다. 이 프로젝트 실측(2026-07-16): 같은 45mm 직선 이동 목표를 30번 솔브했더니 6번(20%)이 J1 +176° / 팔꿈치 반전짜리 해 — 로봇 입장에서는 "그리퍼를 45mm 앞으로"가 아니라 "팔 전체를 휘둘러 반대 자세로 재배치"가 되고, 그 과정에서 링크가 바닥을 관통하는 것처럼 보인다.

교훈: **"EE 목표만 주는 IK"와 "경로를 계획하는 모션 플래닝"은 다르다.** cuRobo MotionGen(플래너)은 시작 관절값에서 연속된 궤적을 만들므로 이런 점프가 없지만, 브릿지의 MoveLine처럼 IK 단발 호출로 관절 목표를 만들면 반드시 **현재 관절에서 가까운 해인지 검사**해야 한다. 수정: 최근접 해 선택 + 최대 관절 이동 45° 가드 + 재시도 (`sim_executor_bridge_node._solve_ik_nearest`). 가드에 걸리면 성공한 척하지 않고 `success=False`로 실패를 알린다 (fail-closed).

## 5. 아키텍처 설계 개념

### Q. 왜 브릿지가 두 개 있어야 하지?

넘어야 할 경계가 두 개라서다 — **언어의 경계**(두산 제어기 전용 서비스 ↔ 범용 표준 메시지)와 **세계의 경계**(ROS 네트워크 ↔ Isaac Sim 프로세스 내부의 물리 세계). `sim_executor_bridge_node`는 두산 제어기인 척 연기하는 프로토콜 번역기, Script Editor 브릿지는 가상 세계의 관절과 딸기를 실제로 만지는 세계 접속기다. 상세 설명과 다이어그램: README의 **"왜 브릿지가 두 개인가"** 섹션.

이 패턴의 일반화: **수정할 수 없는(하고 싶지 않은) 코드가 기대하는 인터페이스를 그대로 흉내 내는 어댑터를 끼워 넣으면, 원본 코드를 거의 바꾸지 않고 다른 환경에서 돌릴 수 있다.** (이 프로젝트에서는 이식 과정의 수정을 `PLANNER_CHANGES.md` 에 남긴다.) 실기 전환 시 어댑터만 빼면 된다.

### Q. fail-closed 설계란? (scan_executor가 시작을 거부한 이유)

`scan_executor_node`는 `/strawberry/scan/start`를 호출해도 기본적으로 거부한다(`execute_motion parameter is false`). 안전이 걸린 시스템에서 **"명시적으로 허가하지 않으면 아무것도 하지 않는다"**는 설계 원칙이 fail-closed다. 반대로 "명시적으로 금지하지 않으면 동작한다"는 fail-open이며, 실물 로봇처럼 오동작이 사고로 이어지는 시스템에서는 fail-closed가 표준이다.

이 노드는 실행까지 여러 겹의 옵트인을 요구한다: `execute_motion:=true` 파라미터, 스캔 후보 YAML의 검증 플래그(`use_for_automated_motion` 등), 명시적 start 트리거, 검증된 overview 자세와 일치하는 live joint state. 거부는 버그가 아니라 **설계가 의도대로 동작한다는 증거**이므로, 통합 테스트에서 START_REJECTED가 나오면 로그의 거부 사유를 순서대로 해소하면 된다.

## 6. 탐색·인식 개념 (2026-09-10)

### Q. 쿼드트리에서 "가지치기"와 "적응 분할"이 정확히 뭐야?

둘 다 트리를 **전부 펼치지 않기 위한** 장치다.

- **가지치기(pruning)**: 부모 노드에서 한 번의 판정으로 자식 서브트리를 통째로 건너뛴다. 이 프로젝트에서는 home(루트)에서 본 원거리 스캔 결과로 "익은 과실이 0개인 분면"을 골라내고, 그 분면의 이동·근거리 스캔·pick 을 전부 생략한다. 판정 없이 네 자식을 무조건 도는 것이 전수 순회(exhaustive traversal)다.
- **적응 분할(adaptive subdivision)**: 모든 칸을 같은 깊이로 쪼개지 않고, 밀도·난이도가 높은 칸만 한 단계 더 쪼갠다. 쿼드트리가 균일 격자와 다른 본질이 여기 있다. 균일 격자는 깊이가 고정이고, 쿼드트리는 칸마다 깊이가 다르다.

깊이 1에 칸이 4개뿐이면 둘 중 하나라도 없을 때 그냥 2×2 격자와 구별이 안 된다. 그래서 "쿼드트리를 썼다"고 말하려면 가지치기 판정과 분할 규칙 중 최소 하나가 코드에 있어야 한다.

### Q. 익음은 세그멘테이션으로 보고 줄기 위치는 키포인트 + 깊이로 보는 이유는? 깊이는 거리랑 같은 말이야?

**무엇을 알고 싶은가에 따라 모델의 출력 형태가 다르다.**

| 알고 싶은 것 | 성질 | 맞는 출력 | 3D 로 만드는 법 |
|---|---|---|---|
| 익었는가 | 과실 **덩어리 전체**의 색·모양 | 세그멘테이션 마스크 + 클래스 | 마스크 중심 픽셀의 깊이 |
| 어디를 잡는가 | 1~2mm 줄기 위의 **한 점** | 키포인트(랜드마크) 픽셀 좌표 | 그 픽셀의 깊이 |

마스크는 "영역"이라 점을 못 찍고, 키포인트는 "점"이라 영역의 속성(색)을 못 준다.

**깊이(depth)** 는 RGB-D 카메라가 픽셀마다 주는 값으로, "카메라 광축 방향으로 그 픽셀이 보는 표면까지의 거리"다. 거리이긴 하지만 ① 픽셀별 값이고 ② 유클리드 거리가 아니라 광축 방향 성분이다. 카메라 내부 파라미터(초점거리·주점)로 (u, v, depth) 를 역투영해야 카메라 기준 3D 점이 되고, TF 로 로봇 base 기준으로 바꾼다.

줄기 키포인트가 까다로운 이유는 줄기가 가늘어 **그 픽셀의 깊이가 줄기가 아니라 뒤의 배경에 찍히기 쉽다**는 데 있다. 그래서 실기 fusion 노드는 반경 몇 px 의 중앙값을 쓰고, 깊이가 없으면 거부하며, 여러 프레임에서 위치가 안정될 때까지 발행을 미룬다. 과실 중심은 덩어리라 이런 문제가 거의 없다. 이 차이가 "멀리서는 과실 존재만, 가까이서만 파지점"이라는 두 단계 인식의 물리적 이유다.

### Q. 분면마다 티칭된 scan pose 가 없으면 무슨 일이 생기는데? (IK 브랜치)

§4 의 "IK 다중해" 와 같은 문제가 **pick 시작 자세**에서 생긴다. 6축 팔은 같은 손끝 위치를 여러 관절 조합(브랜치)으로 만들고, 플래너는 지금 관절 자세에서 연속된 궤적을 만든다. 시작 자세가 그 영역에 맞지 않는 브랜치면 두 가지 중 하나다.

1. 목표 근처의 해가 다른 브랜치에만 있어 IK 가 실패하거나(`IK_FAIL`), 관절 스윙 가드에 걸려 거부된다. 못 집는다.
2. 해는 나오는데 팔 전체를 뒤집는 재배치 궤적이 된다. 보드 옆에서 큰 스윙이 나고, 시뮬 브릿지에서는 이것이 elbow-flip 다이브로 나타났다.

실기 기록(`compute_nw_pick_ready_pose.py`)에서는 분면 중심 한 자세에서 출발하면 팔꿈치를 거의 편 특이점 근처 해만 나와 보드면까지 못 갔고, 세부 칸 중심 자세에서 출발하면 관절 변화 18~36° 로 보드면까지 계획이 됐다. 영역마다 자세를 티칭한다는 것은 **"이 영역의 pick 은 이 브랜치에서 시작한다"를 미리 정해 두는 것**이다.

### Q. 명령 속도를 올려도 로봇이 빨라지지 않는다? (스텝 수와 IK 비용)

가상 제어기 브릿지의 MoveLine 은 실기 `movel` 을 흉내 내려고 **직선을 2mm 씩 잘라 스텝마다 IK 를 푼다.**
그래서 한 번의 직선 이동에 드는 시간은 두 항의 합이다.

```
실소요 = 스텝 수 × (IK 1회 시간 + 스텝 간 sleep)
       = 스텝 수 × IK 1회 시간  +  계획 페이싱(total_sec)
```

두 번째 항은 명령 속도로 정해지는 값이고(예: 120mm / 40mm/s / 배속 2 = 1.5초), 첫 번째 항은
**명령 속도와 무관**하다. 10:13 런 실측에서 IK 1회는 거리와 상관없이 144~153ms 였다.

| 명령 | 스텝 | IK 항 | 페이싱 항 | 실소요 |
|---|---|---|---|---|
| 45mm | 23 | 3.4초 | 0.4초 | 3.4초 |
| 120mm | 60 | 9.0초 | 1.5초 | 9.2초 |

즉 120mm 하강은 명령 속도를 두 배로 올려도 페이싱 항 1.5초가 0.75초로 줄 뿐, 9초는 그대로다.
줄일 수 있는 것은 **스텝 수**뿐이다. 스텝 수 상한을 24 로 두면 120mm 는 5mm 스텝이 되어
IK 항이 3.6초로 떨어진다. 파지 진입 45mm 는 23스텝이라 상한 아래이므로 변하지 않는다.

일반화하면: **이산 명령을 순차로 만들어 보내는 구조에서는, 한 명령을 만드는 비용 × 명령 개수가
"속도"를 결정한다.** 속도 파라미터는 그 뒤에 붙는 대기 시간만 조절한다. 실기 두산 제어기는
직선 보간을 자기 안에서 하므로 이 비용이 없다 — 이 9초는 시뮬에만 있는 인공물이고, 걷어내는
쪽이 오히려 실기에 가까워진다.
