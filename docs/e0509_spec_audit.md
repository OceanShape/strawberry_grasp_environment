## 7. C4 부록 — "J6 설정을 ±225 로 통일하면 회복되나" 오프라인 A/B (2026-09-14)

실기 노드의 J6 설정은 세 곳이 다르다: cuRobo URDF ±360, 실행기 `_JOINT_LIMITS_RAD` ±359(MoveJ 등가 선택 창), 플래너 운용 한계 ±225(09-08 에 ±360 으로 넓힘).
"cuRobo 도 ±225 로 맞추면 플래너가 자기 해를 거부하는 일이 사라져 배치가 회복된다"는 가설을 런 10 후퇴 자세 8개 × 슬롯 8칸으로 검증했다
(`check_tray_slot_reachability.py`, 스윙 가드 원본, 후퇴 자세 J6 는 ±225 등가로 표현). 파일: `log/m3/20260912T013357-ea2ae427/tray_reachability_run10_*.txt`.

| 구성 | 런 10 배정대로 배치 | 못 놓는 과실과 이유 |
|---|---|---|
| A 현재 (cuRobo ±360 · 플래너 ±360) | **6/8** | ripe_07 J2 swing 103>100, ripe_08 J3 swing |
| C4 플래너만 ±225 (cuRobo ±360) | **4/8** | ripe_07·ripe_01·ripe_03 `spline_jump J6`, ripe_08 J3 |
| B 둘 다 ±225 (통일안) | **4/8** | ripe_07 J2, ripe_01 `swing J6`, ripe_08 J3, ripe_06 `limit J1` |

- **통일해도 회복되지 않는다.** 거부 이유만 `spline_jump J6` 에서 `swing J6`·`limit J1` 로 바뀐다. ±225 안에 있는 트레이 해는 후퇴 자세에서 손목을 180° 넘게 돌려야 하거나(이송 스윙 가드 J6 180°),
  J1 이 190° 근처인 반대 팔 분기라(운용 한계 ±225 안이지만 J1 스윙 170° 초과) 어느 쪽도 가드에 걸린다. 원인은 설정 불일치가 아니라 **티칭된 트레이 자세의 손목 방향과 후퇴 자세의 조합이 ±225 창에 안 들어가는 것**이다.
- 그래서 09-08 의 ±360 확장은 "설정을 맞춘 것"이 아니라 "창을 넓혀 통과시킨 것"이었고, 그 둘은 결과가 다르다.
- **판정**: cuRobo 설정은 건드리지 않는다(실기 노드 변경인데 얻는 것이 없다). C4 는 플래너 ±225 원복만 하고, 세 곳의 불일치와 이 A/B 를 실기 노드 기록 사항으로 남긴다. 화면 결과는 8개 중 4개 배치, 4개는 후퇴 자세에서 릴리스.
- **후속 (2026-09-16)**: 이 불일치가 동작으로 드러났다. 실행기 `_JOINT_LIMITS_RAD` ±359 창이 J6 를 ±225 밖(244.4 등)에 세우면 플래너가 다음 궤적을 ±225 로 고쳐 쓰며 첫 점이 로봇 위치에서 360° 떨어져, 브릿지가 플랜지를 한 바퀴 돌렸다(런 14·09-16 런 픽당 2회). 실행기 J6 창을 플래너와 같은 ±225 로 맞춰 없앴다(설계 불일치, `portfolio/H_scope_decisions.md` §11). 이제 J6 는 cuRobo ±360 / 실행기 MoveJoint 창 ±225 / 플래너 ±225 다.

**이력**: 09-14 1판은 카탈로그를 상위 출처로 두고 C1~C7 을 적었다(미적용). 같은 날 사용자 지시로 공식 URDF 를 기준으로 다시 썼다.
1판의 C1(J5)·C2·C3(속도)은 §3 의 결정 항목 D1·D2 로, C4·C5·C6 은 C2·C3·C1 로, C7 은 C4 로 옮겼고, 1판 §3 의 속도 초과 주장은 §1-3 에서 정정했다.

## 6. 관절 가속도 — 필요한가, 어디에 (2026-09-14 추가)

**출처**: 두산 공식 MoveIt 설정 `src/doosan_robot2/dsr_moveit2/dsr_moveit_config_e0509/config/joint_limits.yaml`
(사용자가 받은 사본과 동일). 속도 120/120/150/225/225/225 °/s, 가속도도 같은 숫자(rad/s² 2.0944/2.0944/2.618/3.927/3.927/3.927),
위치 J1·J4·J6 ±180°, J2 ±95°, J3 ±135°, J5 ±135°. `dsr_hardware2/src/dsr_hw_interface2.cpp:305` 는 스트리밍 제어 기본 한계를 전 관절 70 °/s·70 °/s² 로 둔다.
두산 하드웨어 가속도 상한은 공개된 것이 없다. 저크는 다루지 않는다(강체 시뮬에서 영향 없음, 사용자 결정).

**이 리포에서 가속도가 들어가는 자리는 세 곳이다.**

| 자리 | 지금 값 | 성격 |
|---|---|---|
| cuRobo `max_acceleration` (실기 플래너 설정, `_baseline` 동일) | 10 rad/s² = **573 °/s²** | 실험실이 실제 로봇에 보낸 궤적의 가속도 한계. 두산 MoveIt 값의 **2.5~4.8배** |
| 스캔 MoveJoint 요청 (실기 실행기 `_movej`, `req.acc = vel × 1.5`) | 120 °/s · **180 °/s²** | 실험실이 실제 로봇에 보낸 명령. J1·J2 는 MoveIt 값(120)의 1.5배 |
| 시뮬 브릿지 실행 | 스플라인: 선형 보간 + 시간 배분(가속 프로파일 없음, 속도 계단) · MoveJoint: 즉시 발행(가속도 = 드라이브 게인이 정함, 사실상 무한) | 본인 구현 |

**판단**

1. **실기와의 사이클 타임·구간 시간 비교는 불가능하다.** 실험실 런의 구간별 시간 로그가 없고(발표 영상뿐), 순회 시퀀스가 다르며(실기 4분면 전수 vs 시뮬 1차 스캔·분할),
   실제 제어기가 시간 지정 스플라인·`acc` 인자를 어떻게 실행하는지(그대로/클램프) 공식 문서에 없다. 시뮬 시간은 "시뮬 안의 부산물"로만 쓴다(G §7 과 같은 규칙). 가속도를 넣어도 이 사실은 안 변한다.
2. **그래서 가속도는 "시간 비교"용이 아니라 "실기 명령보다 빠르지 않게" 용으로만 필요하다** — 규칙 0. 지금 시뮬은 MoveJoint 를 즉시 발행해 가속도가 사실상 무한이고, 스플라인은 속도 계단으로 시작한다. 이 둘은 실기 명령보다 관대하다.
3. **넣는 자리는 브릿지(본인 구현)뿐이다.** MoveJoint 는 실기 노드가 보낸 vel·acc(120 °/s·180 °/s²)로 사다리꼴 프로파일을 만들어 발행한다(C2 의 구체안). 스플라인은 cuRobo 궤적에 가속도(573 °/s² 한계)가 이미 들어 있으므로 요청 시간대로 실행하면 된다(C3).
4. **cuRobo `max_acceleration` 과 MoveJoint `acc` 는 실기 노드 값이라 건드리지 않는다.** 두산 MoveIt 값보다 크다는 사실은 실기 노드의 한계·기록 사항이다(§2 C4·H §9 와 같은 부류). 실험실 값을 두산 값으로 바꾸면 시뮬이 실제 명령보다 **엄격**해져 검증 대상이 달라진다.
5. **두산 MoveIt yaml 을 쓸 곳은 브릿지 상한 하나다.** 실기 노드가 두산 MoveIt 값을 넘는 가속도를 요청해도 실제 제어기가 그대로 실행한다는 보장이 없으므로,
   브릿지가 `min(요청 acc, yaml acc)` 로 자를지는 선택이다. 자르면 "두산 제어기 설정보다 빠르지 않다", 안 자르면 "실기 명령을 그대로 실행한다". 둘 중 하나를 문서에 명시한다. 권장은 **안 자르고 요청값대로 + 초과 사실 기록** — 검증 대상은 실기 노드의 명령이기 때문이다. **이 선택을 §3 표에 D3 으로 올렸다.**
6. **부수 발견**: 실기 cuRobo URDF 의 J2 ±95·J3 ±135·J5 ±135 는 이 yaml 의 위치 한계와 정확히 같다 — 실험실 운용 범위의 출처가 두산 MoveIt 설정이었다.
   반면 속도는 yaml(120/150)이 아니라 URDF(180)를 썼다(§3 D2). yaml 의 J1·J4·J6 ±180° 는 MoveIt 편의 한계라 실기 플래너의 ±225·±360 을 문제 삼지 않는다.
